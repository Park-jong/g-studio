# __GAME_TITLE__

__GAME_PITCH__

기술 스택: Phaser 4 + TypeScript + Vite, 테스트 vitest. gamestudio 프레임워크로 만든 프로젝트다.

## 명령어
| 명령 | 설명 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm test` | vitest |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run build` | 타입 검사 후 `dist/` 빌드 |
| `npm run preview` | 빌드 결과 미리보기 |

## 문서
| 파일 | 내용 |
|---|---|
| `TODO.md` | 전체 로드맵: 단계별 작업 목록, 현재 상태, 결정 대기, 코드가 정한 해석, 결정 기록 (**작업 전에 먼저 읽는다**) |
| `docs/design.md` | 게임 설계 (콘셉트·핵심 루프·화면·아트 방향) |
| `docs/numbers.md` | 세부 수치 (코드의 `src/data`와 일치해야 함) |
| `docs/skins.md` | 스킨 등록·적용 설계 (스킨 단계에서 생성) |
| `docs/verification-issues.md` | 검증에서 나온 문제와 재발 방지 규칙 (**코드 작성 전에 읽는다**, 반복될수록 ⚠️·🚨로 강조) |
| `CHANGELOG.md` | 버전별 변경 |
| `.dev-team/` | 팀별 로드맵·업무 기록, 타 팀 요청 (gamestudio가 관리) |

## 폴더
```
src/config.ts      해상도·화면 방향·저장 키 접두사
src/core/          Phaser 비의존 공용 도구 (rng, storage, debugParams, orientation)
src/data/          수치·정의 데이터 (게임 로직에 숫자를 하드코딩하지 않는다)
src/<도메인>/       Phaser 비의존 게임 규칙 (예: battle/, run/) — 테스트 대상
src/scenes/        Phaser 화면 (입력·표시만, 규칙은 도메인 모듈 호출)
src/skins/         스킨 등록부·선택·CharacterView (외형은 수치와 분리)
src/session.ts     씬이 함께 쓰는 서비스 (저장, RNG, 스킨 선택)
public/assets/     이미지·사운드 (url은 상대 경로 'assets/...')
prototype/         초기 프로토타입 (보존, 수정하지 않음)
docs/verification-issues.md  검증 문제 기록 (dev-cycle이 만들고 QA 팀장만 수정)
```

## 확인용 URL
- `?stage=N` 타이틀을 건너뛰고 N번 스테이지로
- `?seed=N` 난수 시드 고정
- `?resetSave=1` 저장 삭제 (URL에 남아 있으면 매번 삭제)
- `?skin=대상키:스킨ID,...` 스킨 임시 적용 (예: `?skin=hero:player:alt`)

## 무엇·어떻게·왜
개발하거나 무언가를 추가·변경할 때는 (dev-cycle이든 직접 수정이든) **시작 전에** 아래 세 가지를 밝힌다.
- **무엇**: 만들거나 바꿀 것과 완료 조건
- **어떻게**: 접근 방법과 바꿀 파일. 방법이 여럿이고 결과가 크게 다르면 후보와 추천을 보여준다
- **왜**: 목적(어떤 문제·요구·재미를 위한 것인지)과 근거(`docs/design.md` 장, `TODO.md` 항목, 사용자 요청)

규칙:
- **무엇**이나 **왜**가 요청과 문서에서 확인되지 않으면 추측으로 채우지 말고 먼저 묻는다.
- 요청에 없는 것을 덧붙이지 않는다. 필요해 보이면 무엇·왜를 적어 제안만 한다.
- 끝나면 무엇을 어떻게 바꿨고 왜 그렇게 했는지 보고한다. 계획과 달라진 점이 있으면 그 이유도 쓴다.
- 이 세 가지는 문서에도 남긴다: `TODO.md` 단계의 "목적", "코드가 정한 해석"의 이유, 커밋 메시지 본문(왜/어떤 동작인지), 이유가 코드로 드러나지 않는 결정의 주석.

## 사전 검토 (개발 내용이 정해지면, 구현 전에)
무엇·어떻게·왜가 정해지면 바로 구현하지 말고 **"이대로 진행하면 어떤 문제가 생기는가"를 한 번 따져 보고 대안을 찾는다.**
- 관련 코드와 문서를 실제로 읽고, 근거가 있는 문제만 많아야 5개 적는다: 문제, 영향(높음/중간/낮음), 근거, 대안(장점/단점).
- 점검할 것: 기존 기능 회귀, 저장 데이터 호환, 성능, 모바일·화면 크기·조작, 수치·밸런스, `TODO.md` 다음 단계나 `design.md`와의 충돌, 테스트하기 어려운 구조, 데이터·로직·화면·스킨 분리, `docs/verification-issues.md` 항목의 재발.
- 대안이 "어떻게"만 바꾸면 반영하고 진행한다. 무엇·왜·범위를 바꿔야 하면 추천과 함께 사용자에게 묻는다.
- 짚을 것이 없으면 "특이 위험 없음"과 이유 한 줄로 끝낸다 (작은 작업에 과한 분석을 하지 않는다).

## 작업 규칙
- 사용자가 시작하라고 한 `TODO.md` 항목만 진행하고, 끝나면 멈추고 보고한다.
- 코드 작업은 `/gamestudio:dev-cycle`(개발 팀 구현 → QA 팀 검증·피드백, 최대 3사이클)로 진행한다. 사용자가 "개발만" 하라고 하면 따른다. 기획·아트까지 걸친 큰 작업은 `/dev-team <작업>`으로 맡긴다.
- 문서에 없는 값은 구현 전에 정해서 지시하고, 정한 내용은 `TODO.md`의 "코드가 정한 해석"에 남긴다.
- 게임 규칙은 Phaser 비의존 모듈에 두고 vitest로 테스트한다. 난수는 `Rng`를 주입받는다.
- 수치는 `src/data/`에 두고 `docs/numbers.md`와 일치시킨다. 씬은 입력·표시만, 캐릭터 표시는 `CharacterView`(스킨)로 한다.
- 확인용 URL 파라미터를 새로 만들면 `src/core/debugParams.ts`와 이 파일의 "확인용 URL"에 함께 적는다.
- 저장 데이터에 필드를 추가할 때 버전을 올리지 말고 sanitize에서 기본값을 채운다 (진행도 초기화 방지).
- 커밋은 요청이 있을 때 `/gamestudio:commit-release`로 한다. 확인 화면에서 `커밋 후 push`를 고르면 push(=GitHub Pages 배포)와 Actions 결과 확인까지 한다.
