# dev-cycle

사용자가 지시한 코드 작업을 **개발 → 검증(+피드백)** 사이클로 처리한다.
메인 세션(나)은 총괄 디렉터로서 조율만 한다. 코드를 직접 고치지 않는다.
조직 규칙(누구를 부를 수 있는지, `[Project Context]` 블록, 기록 파일, 타 팀 요청, 언어)은 이 스킬 폴더 기준 `../../guides/director.md`를 따른다. 시작할 때 그 파일을 읽는다. 팀장에게 보내는 프롬프트는 영어로 쓴다.

| 단계 | 부르는 agent | 하는 일 |
|------|-------------|---------|
| 개발 | `gamestudio:tech-lead` | 프로그래머에게 나눠 구현. 프로그래머는 검증 문제 기록을 먼저 읽고 구현한다 |
| 검증 + 피드백 | `gamestudio:qa-lead` | **가벼운 검증**이면 직접 검사를 돌리고, **전체 검증**이면 테스터(테스트·빌드·브라우저 확인, 재발 확인)와 코드 리뷰어(diff 리뷰)에게 맡긴다. 결과를 종합해 판정·근본 원인·수정 지시를 내리고 **검증 문제 기록을 작성·병합** |

## 검증 강도

작은 수정에 매번 테스터와 코드 리뷰어를 모두 돌리면 검증이 구현보다 오래 걸린다. 0단계에서 메인 세션이 강도를 정해 `[Task Spec]`에 적는다.

| 강도 | 언제 | QA가 하는 일 |
|---|---|---|
| **light** (가벼운 검증, 기본) | 버그 수정, 수치·문구 조정, 기존 구조 안의 작은 기능, 바뀌는 파일이 대략 3개 이하 | QA 팀장이 팀원 없이 직접: 검사 명령(typecheck·test·build) 실행, 완료 조건과 사전 검토 위험 확인, 🚨·⚠️ 기록 항목의 재발 확인 |
| **full** (전체 검증) | 새 시스템·화면, 여러 모듈에 걸친 구조 변경, 저장 데이터 형식·네트워크·보안 변경, **단계(TODO.md의 N단계)의 마지막 항목** | 테스터 + 코드 리뷰어(diff 중심)를 병렬로 |

- QA 팀장은 light로 받았어도 위험이 보이면(구조가 크게 바뀜, 테스트가 없는 영역 등) 스스로 full로 올리고 이유를 보고한다.
- **사이클 2~3은 범위를 좁힌다**: 직전에 지적된 항목이 고쳐졌는지와 전체 테스트(회귀)만 확인한다. 전체 리뷰를 처음부터 다시 하지 않는다. 코드 리뷰어는 직전에 must fix를 낸 경우에만, 수정 diff만 다시 본다.

기획이 먼저 필요한 작업(규칙·수치가 문서에 없음)이면 개발 전에 기획 팀장(`gamestudio:design-lead`)에게 맡기거나, 사용자와 정해야 하면 `/gamestudio:game-spec`으로 먼저 정한다. 아트·사운드 산출물이 필요하면 콘텐츠 팀장을 개발과 함께 부른다.

## 검증 문제 기록 (`docs/verification-issues.md`)

검증에서 나온 문제를 **재발 방지 규칙**으로 모아 두는 파일이다. 같은 실수를 다음 작업에서 반복하지 않게 하는 것이 목적이다.

- **작성**: QA 팀장만 고친다 (메인 세션은 없을 때 템플릿으로 만들기만 한다). 다른 agent의 쓰기는 훅이 막는다.
- **병합·강조·횟수 규칙**: QA 팀장 정의(`agents/qa-lead.md`)와 파일 맨 위 설명을 따른다. 요약: 같은 근본 원인이면 새 항목 대신 합치고, 2회 `⚠️`, 3회 이상 `🚨`(맨 위 섹션). 한 작업 안에서 사이클 1~3에 걸쳐 남아 있어도 1회로 센다.
- **읽기**: 프로그래머는 코드를 쓰기 전에 이 파일 전체를 읽는다. 파일이 있으면 훅이 프로그래머 프롬프트에 "먼저 읽어라"는 지시와 `🚨` 규칙을 자동으로 붙인다.
- 파일이 없으면 0단계에서 이 스킬 폴더의 `verification-issues-template.md`로 만든다.

## 0. 준비

1. 프로젝트 지침(`CLAUDE.md`, `TODO.md`, `.dev-team/requests.md`)과 관련 파일을 확인해, 넘길 맥락(대상 파일, 컨벤션, 테스트·빌드 명령)을 모은다.
2. 지시 내용을 **작업 명세**로 정리한다. 모든 팀장에게 `[Project Context]` 블록 다음에 이 명세를 그대로 넘긴다 (영어로 옮겨서).

   ```
   [Task Spec]
   - What: <만들거나 바꿀 것> / Done when: <완료 조건 목록>
   - How: <접근 방법, 바꿀 파일·모듈, 활용할 기존 구조>
   - Why: <목적 — 어떤 문제·요구·재미를 위한 것인지> (source: design.md N장 / TODO 항목 / 사용자 요청)
   - Out of scope: <이번에 하지 않는 것>
   - Verification: light | full — <이유 한 줄> (아래 "검증 강도" 기준)
   ```

   - **무엇**이나 **왜**가 지시와 문서에서 확인되지 않으면 추측으로 채우지 말고 **시작 전에 사용자에게 묻는다.** "왜"가 없으면 같은 "무엇"도 다르게 구현될 수 있다 (예: "적 속도 올려줘"가 난이도 때문인지, 한 판 길이 때문인지).
   - **어떻게**는 내가 정해도 된다. 방법이 여럿이고 결과(구조·성능·플레이 감각)가 크게 다르면 후보와 추천을 보여주고 묻는다.
3. `docs/verification-issues.md`가 없으면 템플릿으로 만든다. 있으면 읽고, 이번 작업과 관련 있어 보이는 항목 ID를 골라 둔다.
4. **사전 검토** — 구현하기 전에 "이대로 진행하면 어떤 문제가 생기는가"를 따져 보고 대안을 찾는다. 관련 코드와 문서를 실제로 읽고 판단한다 (일반론 금지).

   ```
   [Pre-review]
   1. Risk: <무엇이 어떻게 잘못될 수 있나> — impact: high/medium/low · evidence: <파일·문서·기록 항목>
      Alternative: <다른 방법> — pros / cons
   Conclusion: proceed as specified / change How / user decision needed
   ```

   - 점검할 것: 기존 기능 회귀(같은 코드를 쓰는 다른 화면·시스템), 저장 데이터 호환, 성능(개체 수·매 프레임 처리), 모바일·화면 크기·조작, 수치·밸런스와 한 판 길이, `TODO.md` 다음 단계나 `design.md`와의 충돌, 테스트하기 어려운 구조, 데이터·로직·화면·스킨 분리 원칙, 검증 문제 기록 항목의 재발 위험.
   - 근거 있는 문제만 많아야 5개. 짚을 것이 없으면 "특이 위험 없음"과 이유 한 줄로 끝낸다.
   - 대안이 "어떻게"만 바꾸면 반영하고 진행한다. 영향 높음 문제를 피하려면 무엇·왜·범위가 바뀌어야 하면 추천과 함께 사용자에게 묻는다.
5. 사용자에게 작업 명세와 사전 검토를 한국어로 보여주고 바로 시작한다 (물어볼 것이 없으면 승인을 기다리지 않는다).

## 1. 사이클 (최대 3회)

각 사이클은 **개발 → 검증** 순서다. 팀장은 이전 대화를 모르므로 매번 프롬프트에 필요한 맥락을 모두 적는다. 팀장 호출은 백그라운드로 실행되므로 완료 보고가 도착한 뒤에 다음 단계로 넘어간다.

### 개발 — `tech-lead`
- 사이클 1: 원래 지시, `[Project Context]`, `[Task Spec]`, `[Pre-review]`(예상 문제와 채택한 대안), 대상 파일, 관련 검증 문제 기록 항목 ID.
- 사이클 2~3: 위 내용에 더해 **직전 QA 팀장의 수정 지시**를 그대로 넘기고, 지시 범위 밖은 고치지 말라고 적는다.
- 받는 것: 무엇·어떻게·왜 재정리, 파일별 변경 표(무엇·어떻게·왜), 사전 검토 대응, 적용한 검증 문제 기록 ID. `(assumed)` 항목이 있으면 검증 전에 사용자에게 확인한다.

### 검증 — `qa-lead`
- 원래 지시, `[Project Context]`, `[Task Spec]`(검증 강도 포함), 변경된 파일 목록, 실행할 테스트·빌드 명령, `[Pre-review]` 예상 문제 목록, 작업 이름(예: `3단계 3-1`)과 오늘 날짜, 사이클 번호와 이력(각 사이클에서 무엇을 고쳤고 무엇이 남았는지).
- 개발 팀의 자체 평가("잘 동작함" 등)는 넘기지 않는다. 독립적으로 판단하게 한다.
- 사이클 2~3에서는 직전 사이클의 문제 목록을 넘기고, **그 항목들의 해결 여부와 회귀(전체 테스트)만** 확인하라고 적는다.
- 받는 것: `Verdict: APPROVED` / `Verdict: CHANGES REQUESTED`, 문제 목록(심각도 high/medium/low, 위치, 재현 방법, 재발 `V<번호>`), 사전 검토 위험별 결과(avoided / occurred / unverified), 수정 지시(CHANGES REQUESTED일 때), **기록 변경 요약**(새 항목, 병합·횟수, 강조 단계 상승), `[Cross-team requests]`.

### 판정
- **APPROVED**: '2. 완료 보고'로 간다. low 문제는 고치지 않는다. QA 팀장이 `[Cross-team requests]`(QA → 개발 팀)로 올린 것을 작업 끝에 요청으로 기록한다.
- **CHANGES REQUESTED** (완료 조건 미충족 또는 high·medium 문제): 수정 지시를 받아 다음 사이클의 개발로 넘어간다.

### 진행 알림
각 단계가 끝날 때마다 사용자에게 한 줄로 알린다 (예: `사이클 1 검증(light): 수정 요청 — high 1, medium 2 (재발 V2)`, `문제 기록: V4 추가, V2 병합 → 3회 🚨`).

## 2. 완료 보고 (승인된 경우)

- 작업 명세와 실제로 한 것의 차이 (없으면 "명세대로")
- 사전 검토의 예상 문제가 각각 어떻게 됐는지 (피함 / 발생해서 수정 / 확인 못 함). 예측하지 못한 문제가 나왔으면 따로 적는다.
- 몇 번째 사이클에서 승인됐는지
- 변경 내역 표 (파일 | 무엇 | 어떻게 | 왜)
- 검증에서 실제로 실행한 테스트·빌드와 결과 (실행하지 못한 검증이 있으면 그렇다고 적는다)
- 확인하지 못한 부분, 기록한 타 팀 요청 (REQ 번호, 우선순위)
- 검증 문제 기록 변경 (추가·병합·강조된 항목). 재발한 항목이 있었으면 따로 알린다.

## 3. 실패 보고 (3번째 사이클도 수정 요청인 경우)

4번째 사이클은 시작하지 않는다. 멈추고 아래를 보고한 뒤 사용자 결정을 기다린다.

- 해결되지 않은 문제 목록 (심각도, 위치, 재현 방법)
- 사이클별 이력: 각 사이클에서 시도한 수정과 그 결과
- 해결되지 않는 이유에 대한 판단 (예: 요구사항끼리 충돌, 설계 변경 필요, 환경 문제로 검증 불가)
- 다음 선택지 2~3개와 추천 (예: 요구사항 조정, 다른 접근으로 사이클 재시작, 부분 완료로 마무리)
- 현재 코드 상태: 수정이 적용된 채로 남아 있다는 사실과 변경된 파일 목록
- 검증 문제 기록 변경

## 규칙

- 사용자가 지시한 범위만 진행한다. 검증 중 범위 밖 문제를 발견하면 고치지 말고 보고와 타 팀 요청으로만 남긴다.
- 사이클 횟수는 수정 요청 → 수정이 일어날 때마다 센다. 사용자가 중간에 지시를 바꾸면 사이클을 1부터 다시 센다.
- 검증 환경 문제(테스트 실행 불가, 의존성 없음 등)로 판정할 수 없으면 사이클을 소모하지 말고 바로 사용자에게 알린다.
- 사용자가 "개발만" 하라고 하면 QA 단계를 건너뛰고, 검증하지 않았다는 사실을 보고에 적는다.
- 커밋·push는 하지 않는다. 사용자가 커밋을 요청하면 그때 `/gamestudio:commit-release`를 쓴다. `docs/verification-issues.md` 변경도 같은 커밋에 포함한다.

## TODO.md 갱신

`TODO.md`가 있으면 완료 보고 직전에 직접 갱신한다 (팀장에게 맡기지 않는다).

- 처리한 항목을 `[x]`로, 진행 중이면 `[~]`로 바꾼다.
- 문서에 없어서 이번에 정한 값을 `## 코드가 정한 해석`에 **무엇을 어떻게 정했고 왜 그렇게 정했는지**와 함께 추가한다.
- 중요한 결정은 `## 결정 기록`에 날짜와 함께 남긴다.
- `## 현재 상태`의 테스트 개수와 다음 할 일을 갱신한다. (버전·커밋 해시는 커밋할 때 commit-release가 채운다.)
